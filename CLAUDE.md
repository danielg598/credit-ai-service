# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this service is

A FastAPI microservice (Python 3.12, port 8000) that scores credit applications. It is
**one node in a larger system**: its only client is `credit-orchestrator` (a Spring Boot
service, not in this repo). It never talks to the core banking system or a frontend directly.

Given an applicant profile it returns: a 0-1000 score, a default probability, the top-5 SHAP
factors behind the decision, and a Spanish-language explanation generated by an LLM (Groq
Llama 3.3 70B). See `README-credit-ai-service.md` for the full write-up (dataset, model
metrics, prompt text, API examples) — it's kept current and worth reading before making
non-trivial changes.

## Commands

```bash
# Setup (Windows PowerShell)
python -m venv venv
.\venv\Scripts\Activate.ps1
pip install --upgrade pip
pip install -r requirements.txt

# Train the model (downloads the ~50KB UCI dataset, ~20s) — required before first run,
# and required again any time app/services/model_service.py's feature handling changes
python scripts/train.py

# Run the dev server
uvicorn app.main:app --reload --port 8000

# Manual testing: http://localhost:8000/docs (Swagger UI) — POST /predict with the
# default example payload, check `decision` matches `probabilidad_default` vs.
# DEFAULT_THRESHOLD, and that `explicacion` is coherent Spanish tied to the SHAP factors.
```

There is no automated test suite yet (pytest is on the README's TODO list) — validate changes
via `/docs` or by calling `/predict` directly.

**`requirements.txt` is UTF-16-encoded** (not UTF-8) — expect garbled output from tools that
assume UTF-8 (grep/cat-style reads). It is also currently missing the `opentelemetry-*`
packages that `app/core/telemetry.py` and `app/api/predict.py` import (they were added to the
venv directly when telemetry was wired in but never synced back into the file) — if you
regenerate `requirements.txt` from the venv, make sure those packages survive.

## Architecture

Every `/predict` request runs three independent stages in sequence, each with its own
resilience story — understanding the boundaries between them matters more than any single
file:

1. **`app/services/model_service.py`** — loads the trained sklearn `Pipeline` (a
   `joblib` bundle at `models/credit_model.joblib`, produced by `scripts/train.py`) and runs
   inference. The bundle and the model itself are loaded once via `@lru_cache`
   (`get_bundle()`), so **the process must be restarted to pick up a freshly retrained model**.
   This module also applies `COP_TO_DM_SCALE` — a documented scale hack that converts COP loan
   amounts into the Deutsche-Mark range the model was trained on (UCI German Credit Data, from
   1990s Germany). It's intentional MVP debt, not a bug; it disappears once the model is
   retrained on real Colombian data (planned as `logreg-colombia-v2`).

2. **`app/services/shap_service.py`** — explains the prediction with `shap.LinearExplainer`
   (optimal for a linear model, O(1) per prediction). The explainer itself is also
   `@lru_cache`d and lazily built on first request (downloads a 200-row UCI background sample,
   ~2-4s cold start — this is why the very first `/predict` call is slow). Technical feature
   names (e.g. `cat__credit_history_A32`) are mapped to Spanish descriptions via the
   `FEATURE_DESCRIPTIONS` dict; unmapped codes fall back to a generic cleaned-up label rather
   than erroring.

3. **`app/services/groq_explainer.py`** — turns the SHAP factors into a natural-language
   Spanish (ES-CO) explanation via Groq's Llama 3.3 70B, temperature 0.3, forced JSON output.
   Wrapped in `tenacity` retry (3 attempts, exponential backoff 2s/4s/8s) for 5xx/rate-limit
   errors. If Groq is still down after retries, `_fallback_explanation()` builds a templated
   explanation locally from the SHAP factors — **the endpoint never blocks on Groq being
   unavailable.**

`app/api/predict.py` orchestrates these three stages under OpenTelemetry spans
(`model.infer`, `shap.explain`, `groq.explain`) and assembles the final `PredictResponse`. Any
exception anywhere in the pipeline is caught and turned into a 500 with the error detail — there
is no partial-failure response.

Cross-cutting pieces:

- **`app/core/config.py`** — typed settings loaded from `.env` via `pydantic-settings`
  (`Settings`, `@lru_cache get_settings()`). Missing required vars (e.g. `GROQ_API_KEY`) fail
  fast at startup rather than mid-request.
- **`app/core/telemetry.py`** — `setup_telemetry(app, service_name)` wires OpenTelemetry +
  `FastAPIInstrumentor` into the FastAPI app, exporting to an OTLP collector (default
  `http://localhost:4318/v1/traces`, overridable via `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`).
  It auto-picks up the `traceparent` header the Spring Boot orchestrator sends, so spans here
  attach as children of the caller's distributed trace. This module is explicitly written to be
  **shared with other services** (its docstring mentions `vault-mock`) — keep it
  service-agnostic if you touch it.
- **`app/schemas/predict.py`** — the `PredictRequest`/`PredictResponse` Pydantic contract.
  `PredictRequest` uses `extra = "allow"`, so unknown fields from the orchestrator are silently
  accepted rather than rejected — a schema change on the Spring Boot side won't break this
  service's parsing, but it also means typos there won't be caught here either.

### Feature naming and the two `Attribute*` -> name mappings

The UCI German Credit dataset uses generic codes (`Attribute1`, `A32`, `A73`, ...). Two places
independently rename `AttributeN` -> semantic names (`checking_status`, `credit_history`, ...):
`scripts/train.py` (at training time) and `shap_service.py`'s `get_explainer()` (to build a
SHAP background set that matches the trained pipeline's expected columns). **These two mappings
must stay in sync** — the code comments call this out explicitly. If you add/rename a feature,
update both.

### Model choice is deliberate, not a placeholder

Logistic Regression (not a tree ensemble) was chosen for regulatory interpretability (SFC can
read linear coefficients directly), O(1) SHAP latency via `LinearExplainer`, and determinism.
Don't swap the model type without accounting for the fact that `shap_service.py` specifically
relies on `LinearExplainer`, which only works for linear models — an ensemble model would need
`TreeExplainer` and a different background-sampling approach.
